# 伴办 · 技术方案

| 项目 | 内容 |
| --- | --- |
| 形态 | 纯静态 PWA（HTML + CSS + 原生 JavaScript） |
| 构建 | 无构建步骤、无 npm 运行时依赖 |
| 数据 | localStorage，本地优先 |
| 解析 | 本地规则解析器（中文），离线可用 |
| 通知 | Web Notifications + Service Worker（能力范围内） |
| 测试 | Node 单元测试 + Edge/CDP 端到端测试 |
| 目标环境 | iOS Safari 16.4+ / Android Chrome、Edge 现代版本 |

---

## 1. 技术选型与理由

### 1.1 为什么不用 React/Vue

MVP 的页面数量、状态复杂度和团队规模都很小，核心难点是**中文解析、时间计算和提醒逻辑**，不是组件复用。引入框架会带来构建链、依赖体积和部署复杂度，而对本 MVP 的收益有限。

因此选择：

- 原生 HTML/CSS/JS；
- 经典 `<script>`（非 ES Module），这样直接双击 `index.html` 也能运行；
- 无第三方字体、无 CDN、无埋点；
- 所有业务代码在本地，断网可用；
- 需要时可用任意静态服务器托管。

> 如果后续团队扩大、页面继续增长，建议迁移到 Vite + TypeScript + React/Vue；数据层和解析器可以原样保留（已按 UMD/纯函数拆分）。

### 1.2 为什么是 PWA 而不是原生

- MVP 要快速验证“自然语言创建 + 四类任务 + 分级提醒”；
- 手机浏览器 / 添加到主屏幕即可使用，分发成本低；
- 无需应用商店审核；
- 代价是后台通知能力受限（见第 7 节），这是明确接受的产品取舍。

### 1.3 技术栈

| 层 | 选型 |
| --- | --- |
| 视图 | 原生 DOM + 模板字符串 + 事件委托 |
| 样式 | 原生 CSS，CSS 变量 + Grid/Flex |
| 状态 | 单一 `state` 对象 + 单次整体渲染 + 局部倒计时更新 |
| 数据 | localStorage 单键 JSON |
| 解析 | 正则 + 规则 + 词表，纯函数 |
| 通知 | Notifications API + Service Worker `showNotification` |
| 图标 | 内联 SVG；应用图标由 Pillow 生成 |
| 测试 | Node `assert` + Edge CDP |

## 3. 架构

```
┌────────────────────────────────────────────────┐
│                     UI 层                       │
│  app.js 路由/页面/弹层   ui.js 组件   app.css   │
└───────────────┬────────────────────────────────┘
                │ 读写 state / 调用纯逻辑
┌───────────────▼────────────────────────────────┐
│                  领域逻辑层                     │
│  parser.js 解析   util.js 时间/重复   notify.js │
└───────────────┬────────────────────────────────┘
                │ 标准化 / 持久化
┌───────────────▼────────────────────────────────┐
│                   数据层                        │
│  store.js：schema、normalize、CRUD、import/export│
│  localStorage: banban.state.v1                  │
└───────────────┬────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────┐
│            平台能力（渐进增强）                  │
│  Notifications API / Service Worker / PWA       │
└────────────────────────────────────────────────┘
```

**单向数据流**

```
用户操作 → 更新 state / Store → Store.save()
        → render() 重绘当前页
        → 定时器局部更新倒计时，不整页重绘
```

- 整页重绘简单、可预测；任务量小，性能足够。
- 倒计时每秒更新，只改 `[data-countdown]` 的文本和 class，不动输入框/焦点。
- 弹层打开时，底层页面不会因为提醒而重绘（避免打断输入）。

## 4. 核心模块

### 4.1 `util.js`

- 本地日期：`startOfDay`、`addDays`、`addMonths`、`combine`、`dateKey`。
- 显示：`formatDate`、`formatDateWithWeek`、`formatRemaining`、`formatOverdue`。
- 重复：`nextOccurrence(rec, after, anchor)`、`describeRecurrence`。
- 杂项：`escapeHTML`、`uid`、`debounce`、`downloadText`、`vibrate`。

所有日期计算使用本地时区，存储使用 ISO UTC 字符串；显示时转回本地。避免“存日期字符串却按 UTC 解析”导致的跨时区偏移。

### 4.2 `parser.js`

解析流水线：

```
原始输入
  ↓
1. 提取标签（# / 【】 / 标签：）
  ↓
2. 提取优先级（先处理“不重要/不急”否定，再处理高优）
  ↓
3. 提取重复规则（工作日、每周一三五、每月5号、每两周…）
  ↓
4. 提取日期（绝对日、相对日、星期、月底、N天后）
  ↓
5. 提取时间（时间段、时刻、相对分钟/小时、时段）
  ↓
6. 判断长期任务关键词
  ↓
7. 合并 dueAt / startAt / recurrence
  ↓
8. 清理标题（去掉已消费片段、口头语、截止词）
  ↓
9. 置信度 + 识别依据 + 警告
```

关键设计：

- **边解析边“挖空”**：匹配到的片段用空格替换，避免“每周一”又被日期解析成“周一”，也方便最终标题清理。
- **先重复后日期**：定期规则的星期优先被消费；日期只处理剩余部分。
- **保守推断**：长期关键词 + 截止时间很近时，优先判为限时；明确出现“长期/进度”等才判长期。
- **可解释**：返回 `matches`（字段、原片段、人类可读标签）和 `warnings`，UI 展示“识别结果”。
- **可修改**：解析结果只是草稿，所有字段进入表单；用户手动改后不再自动覆盖。
- **时间兜底**：只给日期 → 23:59 但 `hasTime=false`；定期无时间 → 20:00；只给过去时刻 → 明天。
- **不抛异常**：任何输入都返回完整结构；空输入返回置信度 0。

正则中的中文数字支持：一、二、两、三……十、十二、二十三、三十一。

### 4.3 `store.js`

- `initialState()`：首次启动写入 8 条示例，`meta.seeded=true`。
- `normalizeTask()`：所有输入的唯一出口；类型/日期/重复/标签/进度在此收敛。
- `completeTask()`：
  - 标记完成；
  - 长期任务将所有阶段补完成，保证进度一致；
  - 定期任务计算下一次并克隆；
  - 记录 `nextTaskId`。
- `reopenTask()`：恢复并撤回自动生成的下一次。
- `stats()`：今日/逾期/长期/定期统计。
- `exportData()` / `importData()`：整机备份与恢复。
- `load()`：损坏时备份 `.broken` 再回退示例。
- 所有写入失败返回 `{ok:false,error}`，不抛到 UI。

### 4.4 `notify.js`

纯函数 `collect(tasks, settings, now)` 计算“此刻应该发什么”，不直接触碰 DOM：

```text
for task in active:
  if 有 dueAt:
    if 已逾期: 生成 overdue 事件（按 repeatMin 分桶）
    elif 长期且有未完成阶段:
      if 阶段逾期 → ms-now
      elif 阶段 <24h → ms-soon
    else:
      依次检查 m30 / h3 / h24，只取最紧迫且未发送的一档
  else if 长期且有阶段:
    阶段提醒
```

- 每个任务一次最多一个事件，避免叠加。
- 事件带 `ledgerKey`；app 在发送后写入 `task.remindersSent`。
- `deliver()`：
  - 页面可见 → 只显示应用内 toast；
  - 页面隐藏且已授权 → `registration.showNotification`；
  - 未授权 → 应用内 toast + 设置引导。
- `nextLeadFor()` 给详情页展示“下一次提醒”。
- `digestEvent()` 独立处理每日简报。

### 4.5 `ui.js`

纯函数输出 HTML 字符串：

- 内联 SVG 图标表（24×24，stroke 1.8）。
- 四类任务颜色/图标元数据。
- `taskCard()`：类型徽章、优先级、时间、倒计时、标签、长期进度。
- `emptyState()`、`sectionHead()`、`segmented()`、`typeFilters()`、`searchHighlight()`。
- 所有用户内容经 `escapeHTML`，搜索词经正则转义。

### 4.6 `app.js`

- Hash 路由：`today / calendar / inbox / search / settings / task/:id`。
- 页面渲染函数返回 HTML；事件委托统一在 `document` 上处理 `data-action`。
- 新建/编辑弹层：`state.composer` 保存草稿；输入防抖解析；字段手动修改标记。
- 提醒循环：每 20 秒 `checkReminders`，每次最多处理一条。
- 时钟循环：每 1 秒更新倒计时；跨截止时检测状态签名并重排。
- 跨标签页：监听 `storage` 同步。
- 系统通知权限必须在用户点击事件中请求。

## 5. 时间与重复算法

### 5.1 为什么不用日期库

需求集中在“本地日历日 + 固定时刻 + 每周/每月/每年”，用原生 `Date` 足够，且避免引入 10–20KB 依赖。关键是自己处理：

- 本地时区构造（`new Date(y, m, d, h, min)`）；
- 月末截断（31 号 → 2 月最后一天）；
- 周相位（周一为内部起点，周日映射为 6）；
- 未来/过去判断；
- DST 跳变时用本地构造器自然处理（中国无 DST，但代码不假设）。

### 5.2 重复算法

```js
nextOccurrence(rec, after, anchor):
  switch rec.freq:
    daily:
      d = anchor 当天 + rec.time
      while (d <= after) d += interval 天
    weekly:
      weekStart = 周一(anchor)
      for week = 0; week < 260; week += interval:
        for weekday in rec.weekdays (默认 anchor 星期):
          candidate = weekStart + week*7 + offset(weekday) + time
          if candidate > after: return candidate
    monthly:
      day = rec.monthDay || anchor 日
      for month = anchor 月; month < +240:
        candidate = 当月 min(day, 月末) + time
        if candidate > after: return candidate
        month += interval
    yearly:
      同上，按年 + 月日，2 月 29 日截断
```

- 完成定期任务时 `after = max(dueAt, now - 1min)`，跳过已经错过的周期。
- 首次生成时 `after = now - 1s`，让“今天稍晚”的周期仍可落在今天。

## 6. 本地存储

- Key：`banban.state.v1`。
- 整体 JSON 读/写，无异步事务。
- 数据量小（<1MB 常见），性能足够。
- 存储失败：捕获 `QuotaExceededError`，提示导出备份。
- 数据损坏：备份到 `.broken`，恢复示例。
- 跨标签页：`storage` 事件重新加载。
- 未来若任务量/附件增长，迁移到 IndexedDB + 分表；数据模型已按可迁移方式设计。

## 7. 通知与后台限制（关键）

### 7.1 已实现链路

```
用户点击“开启”
  → Notification.requestPermission()
  → 注册 Service Worker
  → 每 20s checkReminders()
      → notify.collect()
      → 页面可见? 应用内 toast : registration.showNotification()
      → 写入 remindersSent
```

- 点系统通知：Service Worker `notificationclick` 聚焦已有窗口，或打开 `#/task/:id`。
- 通知带 `tag`、`renotify`，避免同一任务堆叠。
- 逾期通知 `requireInteraction: true`（支持的平台会驻留）。

### 7.2 为什么不能承诺“关掉浏览器也准时”

纯 Web 没有可靠的后台定时器：

- 页面关闭后 JS 定时器停止；
- Service Worker 不能长期常驻，也不能自行定时唤醒（除非 Push/Periodic Sync，且需要服务器/平台支持）；
- iOS 对网页后台和通知更严格，通常要求“添加到主屏幕”且用户授权。

所以 MVP 的提醒是**页面/PWA 存活时最可靠**，完全关闭后不保证。产品在设置页明确说明，并提供“安装到主屏幕”的建议。

### 7.3 Phase 4 原生方案（推荐）

若“截止前一定响”是硬指标：

- 用 Capacitor 封装现有 Web 应用（代码复用 90%+）；
- 使用 `@capacitor/local-notifications` 在本地注册系统级定时通知；
- 在任务保存/修改时重新排程，完成/删除时取消；
- 保留 Web 版作为预览/备份；
- 后续可选接入系统日历（EventKit / CalendarContract）。

这比在 Web 里堆 hack 更可靠，也不破坏“无后台”的 MVP 约束。

## 8. PWA 与离线

### 8.1 Manifest

- `display: standalone`、`orientation: portrait`、主题色暖纸色；
- 192/512/maskable 图标；
- 快捷方式：看今天、打开收件箱。

### 8.2 Service Worker

- 安装时预缓存应用外壳（HTML/CSS/JS/图标/Manifest）；
- 导航请求：网络优先，失败回退缓存的 `index.html`；
- 静态资源：缓存优先，后台更新；
- `skipWaiting` + `clients.claim`；
- 更新时删除旧 cache（版本号 `banban-shell-v3`，每次发布递增）。

### 8.3 安装与 HTTPS

- Service Worker / 通知需要安全上下文：HTTPS 或 localhost。
- 本地开发：`http://localhost:4173` 可用。
- 手机通过局域网 IP 访问时，不是安全上下文，通知/PWA 安装可能不可用；正式体验请部署到 HTTPS（Vercel / Netlify / GitHub Pages / 自有服务器）。
- iOS：Safari 分享 → 添加到主屏幕；从主屏幕打开后申请通知权限。

## 9. 安全与隐私

| 项目 | 措施 |
| --- | --- |
| 数据 | 不离开设备，无账号、无服务端 |
| XSS | 所有动态文本 `escapeHTML`；搜索高亮前先转义 |

| 依赖 | 无第三方脚本/字体/CDN；供应链风险低 |
| 备份 | 用户主动导出；无自动云上传 |
| 可见性 | 设置页明确“仅本机”与通知限制 |

## 10. 性能

- 首屏资源：约 6 个 JS/CSS 文件，未压缩总量 < 100KB；无外部请求。
- 首屏渲染：全量 HTML 字符串，任务 1000 条内一次渲染可接受；列表未做虚拟滚动（MVP 规模）。
- 倒计时：每秒只查询 `[data-countdown]`，不重绘整页。
- 提醒检查：20 秒一次，任务量小；`collect` O(n)。
- Service Worker：缓存优先，二次打开接近即时。
- 动画：CSS transform/opacity；支持减少动效。
- 可优化项（后续）：虚拟列表、按需渲染月份、IndexedDB、压缩构建。

## 14. 关键实现片段

### 14.1 完成定期任务

```js
const afterBase =
  task.dueAt && new Date(task.dueAt) > now - 60000
    ? new Date(task.dueAt)
    : new Date(now - 60000);
const nextDue = U.nextOccurrence(task.recurrence, afterBase, anchor);
const next = normalizeTask({
  ...task,
  id: uid('task'),
  status: 'active',
  dueAt: nextDue.toISOString(),
  completedAt: null,
  remindersSent: {},
  nextTaskId: null,
});
task.nextTaskId = next.id;
```
